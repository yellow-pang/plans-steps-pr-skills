# v3 첫 구현 재검토와 변경 전후 비교

검토일: 2026-09-27. 비교 기준은 첫 구현 커밋 `e8e9328`, 보완 결과는 `24205fe`다. 사용자 요청에 따라 먼저 첫 구현 28개 파일을 커밋하고, 그 상태를 기준으로 설계 대조와 보완을 수행했다. 보완도 후속 요청에 따라 커밋했다. Push·PR은 수행하지 않았다.

## 판단과 근거의 범위

**7개 역할과 핵심 방향은 맞았지만, 문서 작성과 실행 결과 확인을 지나치게 압축한 부분이 있었다.** 특히 한국어 커밋 기본값은 기존 main에서 명시됐으나 첫 v3 구현에서 빠졌고, Steps는 “작업 규모에 맞게”라는 지침만으로 충분한 설명 수준을 정하게 했다. 구조 오류보다 실제 산출물의 누락과 판단 편차가 주요 문제였다.

검토 기준은 [승인된 설계](../04-v3-upgrade-considerations.md), main 원문, 기준 커밋의 7개 Skill과 reference 5개, 이번 사용자 요구다. 예상 사용 장면은 사용자가 설명한 API·저장·백그라운드 처리·브라우저·화면 표시가 연결된 개발 과정이다. 실제 사용자 제품 저장소를 별도로 조사한 것은 아니다.

이 검토는 같은 세션에서 수행한 자체 점검이다. **아래 모델 위험은 Sol Medium의 실측 실패가 아니라, 지시문 누락·모호성에서 예상한 위험**이다. 이전의 subagent 비사용 요청을 유지했고 별도 Sol Medium 모델 실행을 하지 않았다. 자동 선택률·실제 준수율은 확인되지 않았다.

## 무엇이 맞았고 무엇을 보완했는가

| 계획 | 사실 조사와 미래 변경 분리, 별도 Review 승인 비강제 | 다음 세션에서 구현할 변경 위치·인터페이스·검증 명령과 필요한 데이터 전환 조건을 명확히 함 |

| PR | 전체 브랜치 차이 확인, 필요한 Push와 자동 Commit의 분리 | 최신 커밋만 요약하지 않도록 전체 범위 대조, 언어·개행·재사용 기준과 실제 본문 확인을 보강 |

## 중요한 발견과 변경 전후

| ID | 기준 커밋의 근거 | 원하는 방향과 어긋날 수 있는 결과 | 보완 후 기준 |
|---|---|---|---|
| R01 | 커밋은 “간결한 Conventional Commit 제목과 필요한 본문”이라고만 함 | 영어 제목만 출력하거나 제목·본문 요청에서도 본문을 생략할 여지. main의 한국어 기본값이 누락됨 | 한국어 기본값과 요청한 제목·본문 제공, 여러 변경의 본문 작성 명시 |
| R02 | 커밋 대상을 확인하라는 지침은 있으나 초안 이후 재대조가 없음 | 추가 변경 뒤에도 앞서 작성한 제목과 본문을 그대로 재사용할 수 있음 | 메시지 직전에 현재 대상 전체를 확인하고 새 변경으로 범위가 달라지면 다시 작성 |
| R03 | 실행 후 SHA·범위만 확인, 저장된 메시지 확인은 없음 | 셸에서 본문을 잘못 전달해 문자 `\n`이 저장돼도 놓칠 수 있음 | UTF-8 파일로 전달하고 실제 Git 객체의 제목·본문·개행을 조회 |
| R04 | Steps는 “작업 규모에 맞게”, “작은 변경이면 짧게” 중심 | 여러 계층 변경도 전문 용어 목록 몇 줄로 압축할 수 있음 | 처음 참여한 독자가 문제·원인·전후 동작·검증을 연결해서 이해할 수준을 기준으로 삼음 |
| R05 | Steps 언어 규칙이 빠지고 용어·그림의 구체 기준이 없음 | 영어 전문 용어로 설명을 대체하거나 그림을 무조건 생략/추가할 수 있음 | 한국어 설명, 첫 등장 용어 풀이, 유용한 경우의 표·흐름도·주석. 실제 근거에 맞는 그림만 사용 |
| R06 | Plan/구현은 기존 Context “갱신”만 언급 | 해당 역할을 단독 사용하면 긴 작업 중 처음 필요한 인계 기록을 만들 시점이 모호함 | 필요한 경우 생성·기본 위치·최소 내용·읽기 전용 대체를 역할 안에 포함 |
| R07 | 현재 코드/runtime 우선, 계약을 바꾸면 선택 확인이라는 짧은 표현 | 현재 버그를 원하는 동작보다 우선하거나 이미 승인된 계약 변경을 재질문할 여지 | 현재 사실과 원하는 요구를 분리하고 요청 밖 새 선택만 확인 |
| R08 | B03은 관측 `ready`와 fixture `pending`의 차이만 제공 | 정상 대기 상태 테스트를 낡은 테스트로 잘못 삭제하는 행동을 평가가 오히려 유도할 수 있음 | 동일 완료 작업·배포 버전의 계약 변경을 제공하고 정상 `pending` 검사는 보존 |
| R09 | 검증 재사용의 내용·환경 조건은 있으나 근거 저장·필수 검사 예외가 짧음 | “같은 상태”라고 기억만 재사용하거나 필요한 CI까지 생략할 여지 | 검사 대상·방법·결과·코드/환경 근거와 요구·위험 변화, 필수 검사 예외를 추가 |

R01과 R03은 구체 출력·실행 확인 기준의 누락이다. R04~R07은 일부 모델이 합리적으로 보완할 수 있더라도, 사용자가 중요한 것으로 명시한 선택을 모델의 암묵적 추론에 맡긴 상태였다. 보완은 이 불확실성을 줄이기 위한 것이며 모델 성능 개선 수치를 주장하지 않는다.

## Steps 문서는 실제로 어떻게 달라졌는가

첫 구현의 문서는 역할 표와 검증 한계를 갖췄지만 “lifecycle 영향 종료”, “fixture 충돌”, “producer/consumer”를 설명 없이 압축했다. 이번에는 [첫 구현 Steps](2026-09-27-v3-skill-implementation.md) 자체를 수정해 사용자 개발 흐름, 원래 지원하던 동작, 부족했던 판단, 전후 역할, Git 요청의 실제 예를 풀어 썼다. 표와 역할 흐름도를 함께 넣었다.

| 항목 | 이전 표현/구성 | 이후 설명 |
|---|---|---|
| 영향 분석 | “producer/consumer와 상태 전이를 확인” | 값을 만드는 API부터 저장·처리·화면 표시까지 확인하는 이유를 설명 |
| 세션 인계 | “Context 인계” | 다음 세션이 잃지 않아야 할 요구·사실·결정 기록이라고 풀이 |
| Git 흐름 | “PREPARE/EXECUTE” | “메시지 보여줘”와 “커밋해줘”에서 각각 어디까지 수행하는지 예시 |
| 시각 자료 | 역할 표만 존재 | 선택 가능한 인계 관계를 흐름도로 보강하고 필수 순서가 아님을 설명 |
| 검증 | 정적 검사 결과 목록 | 최초 결과와 후속 결과, 형식 검사와 실제 모델 행동의 차이를 구분 |

짧은 문서를 무조건 길게 만드는 기준은 아니다. 문구 하나를 바꾼 작업은 전후 문구와 확인 방법만으로도 이해할 수 있다. 여러 처리 단계가 연결된 작업은 그 연결과 실패 조건을 설명해야 하므로 필요한 분량이 늘어난다. 그림 렌더링은 수행하지 않았으며 이해를 돕는 Markdown/Mermaid 원문을 추가한 상태다.

## reference를 추가한 이유

새 reference는 두 개다. 각 Skill 본문에서 읽을 상황을 안내하고 다른 Skill 폴더에 의존하지 않는다.

| 파일 | 담은 내용 | 별도 파일로 둔 이유 |
|---|---|---|
| [Steps 작성 기준](../../skills/steps-documentation/references/writing-guide.md) | 적절한 설명 깊이, 부족한/충분한 설명 예시, 용어·그림·검증 근거 | 복합 변경을 기록할 때 필요한 상세 예시이며 작은 작업에는 전부 읽을 필요가 없음 |
| [커밋 메시지 작성](../../skills/commit-workflow/references/message-writing.md) | 전체 범위, 한국어 제목·본문, 실제 개행과 형식 예시 | 메시지 품질과 실행 절차가 서로 다른 상세 책임이므로 기존 실행 reference와 분리 |

검증·검토·Provider reference는 기존 파일을 보강했다. 분석·Plan에 새 reference를 추가하지 않은 이유는 부족한 핵심 조건을 본문 몇 문장으로 해결할 수 있었기 때문이다. 규칙 동기화 생성기, 별도 상태 머신, 새 역할, Plugin 파일은 추가하지 않았다.

B01·B04·B05는 이번 발견과 무관한 평가 확대 없이 유지했다. 문구·heading·파일별 테스트는 만들지 않았고 새 상시 테스트 스크립트도 추가하지 않았다. 보고서·메시지 내용은 실제 diff와 수동 대조했으며 모델의 독립 평가로 표현하지 않는다.

## 비교와 다음 작업

두 커밋의 차이가 보완 전후 결과다. 아래 명령은 새 reference 2개와 이 보고서를 포함한 변경을 보여준다. 현재 상태는 별도로 `git status --short`로 확인한다.

보완 커밋 `24205fe`는 Skill 7개를 유지하고 reference를 5개에서 7개로 늘렸다. README·인계 문서는 이번 비교 문서를 현재 재개 지점으로 안내하도록 갱신했다.

```powershell
git diff e8e9328 24205fe -- skills tests/behavior docs/steps
git show e8e9328:skills/steps-documentation/SKILL.md
git show e8e9328:skills/commit-workflow/SKILL.md
git status --short
```

다음 검증은 격리된 Sol Medium 세션에서 B02의 결과 문서와 B06의 메시지 요청을 먼저 관측하는 것이 적절하다. 그 실행이 허용된 범위에서 실제 Skill 노출 경로·모델·도구·출력을 기록해야 한다. 현재 설치 캐시나 Plugin에 v3를 배포하지 않았으므로 이 저장소의 수정이 설치된 v2를 바꾸지는 않는다. 다른 모델의 자기 점검을 Sol Medium 통과로 취급하지 않는다.
