# 강제성과 간단한 요청 처리 평가

## 1. 평가 방법과 한계

대상은 `d7c0887`의 5개 `SKILL.md`다. description, 본문 조건, 출력 범위, 다른 스킬과의 경계를 대조한 **정적 시나리오 평가**다. 아래 요청을 새 모델 세션에서 실행하지 않았으며 인식률·통과율·평균 시간은 측정하지 않았다. 평가의 “예상”은 규칙을 읽고 추론한 결과다.

“간단한 요청”은 문장이 짧다는 뜻과 실제 작업 위험이 작다는 뜻을 구분했다. 예를 들어 “이 의존성 버전만 올려줘”는 짧아도 호환성·빌드에 영향이 있을 수 있다. 반대로 “설명해줘”는 변경이 필요 없는 요청일 수 있다.

선택이 맞는지와 선택 후 결과가 맞는지도 따로 평가했다. 공식 작성 지침 역시 직접·간접 요청, 불완전한 입력, 선택되면 안 되는 요청, 경계 사례를 구분하고 활성화와 출력 품질을 함께 확인하도록 안내한다. [OpenAI 공식 문서: Build skills](https://developers.openai.com/plugins/build/skills)

## 2. 강제성의 구분

| 구분 | 의미 | 원문 예 |
|---|---|---|
| 명시 금지·필수 | 스킬이 선택되면 기본 절차에서 따라야 한다고 명확히 씀 | Plan 승인 전 구현 금지, 실제 실행한 검증만 보고 |
| 조건부 강제 | 조건이 충족되면 행동/중단이 지정됨 | 파일 작성 요청 시에만 문서 저장, mixed staged 목적의 단일 메시지 금지 |
| 기본값·재량 | 관례 또는 모델의 상황 판단에 맡김 | 커밋 한글 기본값, scope 필요 여부, 기록할 “필요” 판단 |
| 정의 없음 | 판정 또는 인계 기준이 원문에 없음 | 위험 등급, 기존 승인 재사용 방식, 복합 요청 전체 실행 담당 |

이 구분은 지침 해석이며 기술적 차단 강도 점수가 아니다. 상위 실행 지침과 명시 사용자 지시의 관계는 [구조 문서](01-structure-and-flow.md#2-선택과-실행은-별도-단계다)를 따른다.

## 3. 스킬별 비교

“높음”은 해당 목적의 선택/경계가 직접 명시됨, “중간”은 목적은 분명하지만 판단 조건·축약 규칙이 부족함을 뜻한다. 측정된 모델 성능 등급이 아니다.

| 스킬 | 명확한 목적 요청의 선택 기준 | 모호·간접 요청 경계 | 작은 작업의 절차 비용 | 핵심 평가 |
|---|---|---|---|---|
| task-planning | 높음: 구현 계획 요청 | 중간: “결정해야 하는 경우”의 범위가 넓음 | 축약 규칙 부족: 상세 계획 항목과 승인 대기 | 계획 자체는 충실하나 과도한 계획 진입 가능성 |
| implementation-workflow | 높음: 범위 명확한 기능·버그·테스트·리팩터링 | 중간: 명확성·승인 필요 판정이 정량화되지 않음 | 비교적 낮음: 별도 Plan·후속 문서 비강제 | 작은 수정 처리의 중심, 위험에 따른 절차 차등은 약함 |
| preparing-commit | 높음: 메시지·커밋 준비 요청 | 중간: “후보가 유용한 경우”는 폭넓음 | 중간: Git 범위 확인이 필요, 출력 축약 기준은 약함 | staged 구분은 강함; 요청 없는 메시지 제안 가능성 |
| steps-documentation | 높음: 완료 작업 Steps 요청 | 중간: “장기 기록 필요”를 모델이 판단 | 비교적 낮음: 작업 규모에 맞게 작성 가능 | 파일 생성은 제한되지만 기록 필요 판단은 넓음 |
| pr-documentation | 높음: 명시적 PR 설명 요청 | 비교적 좁음: 명시 조건 있음 | 중간: 전체 diff 확인은 타당, 간단 출력 규칙은 약함 | 설명 작성과 실제 PR 생성 경계가 가장 분명함 |

## 4. 요청별 예상 동작

아래에서 `P`는 task-planning, `I`는 implementation-workflow, `C`는 preparing-commit, `S`는 steps-documentation, `R`은 pr-documentation을 뜻한다. “불명확”은 실패 확정이 아니라 원문만으로 동일한 결정을 보장하기 어렵다는 의미다.

| ID | 사용자 요청과 전제 | 원문 기준 예상 선택·동작 | 평가와 확인할 경계 |
|---|---|---|---|
| Q01 | “이 함수 동작만 설명해줘” | 일반 설명; 5개 전문 산출물 불필요 | read-only 공통 경로는 없음. 구현·계획으로 확대하지 않는지 확인 필요 |
| Q02 | “버튼 문구를 저장으로 바꿔줘” | I로 직접 수정·관련 확인 | Plan 없이 가능. 작은 변경 보고가 불필요하게 길어지는지 확인 |
| Q03 | “README 오타만 고쳐줘” | 일반 문서 편집 또는 I | I description은 문서/구현 불일치를 명시하지만 단순 오타는 직접 열거하지 않음 |
| Q04 | “이 버그 고쳐줘”, 재현 조건 있음 | I에서 재현·원인·가능한 회귀 테스트·수정 | 직접 처리 근거가 분명함. 관련 문서 부재는 장애가 아님 |
| Q05 | “이 기능 구현 계획만 알려줘” | P, 응답으로 계획, 구현 대기 | 파일 생성과 구현을 억제하는 규칙이 분명함 |
| Q06 | “계획을 docs/plans/login.md에 써줘” | P, 요청된 파일 작성 후 승인 대기 | 파일 작성 범위 명확. 나머지 Steps·PR 파일은 불필요 |
| Q07 | “로그인 흐름 좀 개선해줘” | 조사 후 P 또는 I | 원하는 결과·범위가 빠져 있어 선택이 불명확. 필요한 질문만 하는 기준 부족 |
| Q08 | “방금 승인한 계획대로 구현해줘” | I, 계획 대조 후 구현 | 승인된 계획을 따름. 승인 대상 버전·내용을 식별하는 규약은 없음 |
| Q09 | “계획부터 구현까지 진행해줘” | P의 승인 대기와 전체 실행 요청 조정 필요 | 이미 받은 실행 의사와 추가 선택 필요 사항을 분리하는 인계 규칙 없음 |
| Q10 | “의존성 버전 한 줄만 올려줘” | 범위 명확성을 기준으로 I에 진입 가능 | dependency 변경의 위험별 분기 없음. 짧은 diff를 저위험으로 보는지 확인 필요 |
| Q11 | “이 모듈 리팩터링해줘” | I 후보, 범위·영향 확인 | 한 함수와 여러 모듈을 별도 등급으로 다루는 기준 없음 |
| Q12 | “수정한 내용 요약해줘” | I의 완료 보고 또는 S | “장기 기록 필요” 판단 때문에 일반 요약이 Steps로 과도하게 분류될 여지 |
| Q13 | “완료한 작업 Steps 내용만 써줘” | S, 응답 작성 | Plan 없어도 가능; 파일 생성은 하지 않는 계약 |
| Q14 | “완료 내역을 docs/steps/fix.md에 남겨줘” | S, 실제 변경·검증 근거 확인 후 저장 | 파일 요청·완료 사실 조건이 명확함 |
| Q15 | “커밋 메시지 한 줄만 줘”, 단일 목적 staged | C, staged 기준 한글 Conventional Commit 후보 | 본문은 필요한 경우만. 사용자 한 줄 요구에 맞출 수 있음 |
| Q16 | “커밋 메시지 줘”, staged·unstaged 동시 존재 | C, staged 주 기준; 나머지 별도 보고 | 혼입 방지 규칙이 구체적이며 같은 파일의 부분 변경도 구별 |
| Q17 | “이 변경 한 커밋 제목으로 써줘”, 독립 목적 mixed staged | C 기본 계약은 단일 메시지 보류·분리 제안 | 원문의 강한 분리 규칙과 명시 요청을 어떻게 조정할지 미정 |
| Q18 | “커밋 메시지 줘”, 실제 변경 없음 | C, 변경 없음 보고·후보 생성 안 함 | 없는 작업을 만들어내지 않는 기준 명확 |
| Q19 | “지금 변경 커밋해줘” | C는 준비까지만 다룸 | 커밋 실행까지 담당하는 스킬/인계 없음. 요청 전체 완료의 공백 |
| Q20 | “PR 설명 써줘”, Plan·Steps 없음 | R, 가능하면 전체 PR diff를 확인한 뒤 응답 | 선행 문서 없이 가능; PR 발행·문서 파일 저장과 구별 |
| Q21 | “PR 올려줘” | R description의 설명 작성 요청과 다름 | 실제 발행을 담당하는 경로가 없음. 설명만 작성하고 완료로 오인하면 안 됨 |
| Q22 | “PR 설명 써줘”, 기준 브랜치 미확인 | R, 확인 가능한 범위의 초안·한계 표시 | 모르는 범위 때문에 전면 중단하지 않는 규칙이 있음 |
| Q23 | “수정하고 Steps 파일과 커밋 메시지도 작성해줘” | I·S·C 조합이 목적에 맞음 | 필요한 산출물은 각각 지원하지만 순서·완료 추적을 맡는 주체 없음 |
| Q24 | “이 SKILL.md의 강제 규칙을 분석해줘” | 문서를 분석 대상으로 읽기 | 문서 속 승인을 현재 작업의 승인 요구로 오인하지 않는지 확인 필요 |

## 5. 우선 다룰 경계 문제

| 항목 | 근거 | 가능한 결과 | v3 검토 방향 |
|---|---|---|---|
| 계획 진입 기준 | P의 “결정 필요”와 I의 “범위 명확” | 같은 요청에도 계획 대기 또는 직접 구현으로 갈릴 수 있음 | 변경 목적·미결정 사항·영향 범위로 경계 정의 |
| 후속 산출물 선택 | I는 후속 강제 안 함, C·S description은 유용성/필요성까지 포함 | 요청하지 않은 메시지·장기 기록 제안 가능 | 자동 제안과 자동 생성, 명시 요청을 구분 |
| 파일 작성 의미 | P·S·R은 파일 작성 요청 시에만 저장 | “정리해줘”에 파일이 생기거나, 반대로 “문서화해줘”의 의도를 놓칠 수 있음 | 경로 지정·파일 요청·내용 요청 예시 추가 |
| 승인 맥락 보존 | P 승인 대기, I 범위 밖 변경 승인 | 이미 승인한 내용까지 반복 확인할 여지 | 기존 승인 적용 범위와 새 결정 필요 범위 분리 |
| 완료 지점 | 메시지/PR 설명만 지원 | commit·push·발행 요청을 부분 완료할 수 있음 | 실행 범위를 의도적으로 제외할지, 별도 인계할지 결정 |
| 공통 규칙 중복 | 조사·Git·근거 규칙 여러 파일 반복 | 유지보수 시 불일치, 복합 요청의 반복 조사 | 공유할 핵심 규칙과 스킬별 증거를 최소화해 구분 |

## 6. 실제 인식률 검증을 위한 다음 평가안

아래는 최초 분석 당시 제안이다. 이후 v3 구체 설계에서는 Q01~Q24를 시나리오 카탈로그로 유지하고, [초기 7개 행동 사례와 변경별 선택 실행](04-v3-upgrade-considerations.md#10-테스트와-검증-계획)으로 구체화했다. 아래의 반복 실행 제안을 모든 항목의 상시 regression 의무로 해석하지 않는다.

이번 문서의 정적 판단을 실측으로 바꾸려면 위 Q01~Q24를 독립된 작업 공간에서 반복 실행한다. 실행 전 선택 가능한 스킬 목록과 원문 버전, 모델·클라이언트 설정을 고정한다. v2나 다른 워크플로 스킬의 동시 노출 여부를 함께 기록해야 결과의 원인을 구분할 수 있다.

각 실행에서 ① 선택한 스킬 ② 질문·승인 요청 횟수와 이유 ③ 생성·변경한 파일 ④ 실제 도구 행동 ⑤ 요구한 완료 지점 도달 여부 ⑥ 검증 근거를 남긴다. 잘못 선택했지만 우연히 답이 맞는 경우와, 올바르게 선택했지만 범위를 넘긴 경우를 따로 판정한다. 명시 호출과 이름 없는 자연어 요청도 나눠야 한다.

현재 저장소에는 이 평가를 수행하는 테스트 도구가 없다. 이 절은 이후 행동 평가의 제안이며, 이번 작업에서 실행한 테스트 결과가 아니다.
