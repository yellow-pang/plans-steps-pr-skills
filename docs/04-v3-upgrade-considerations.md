# v3 업그레이드 검토 사항

이 문서는 기존 스킬 분석에서 도출한 **설계 후보**다. v3의 승인된 구현 계획이나 사용자의 현재 작업 방식이 확정되었다는 기록이 아니다. 이번 작업에서는 스킬·플러그인 설정을 변경하지 않는다.

## 1. 기존 구성에서 유지할 가치

| 유지할 원칙 | 이유 | 근거 |
|---|---|---|
| 범위가 명확하면 Plan 없이 구현 가능 | 단순 수정의 시작 비용을 줄임 | [implementation-workflow](../skills/implementation-workflow/SKILL.md#핵심-원칙) |
| Plan·Steps·PR 간 선행 문서 비강제 | 필요한 산출물만 만들 수 있음 | [구조와 흐름](01-structure-and-flow.md) |
| 실제 diff·코드·실행 기록 우선 | 계획과 실제 결과를 혼동하지 않음 | [Steps 작성 전 확인](../skills/steps-documentation/SKILL.md#작성-전-확인) |
| staged·unstaged·untracked 분리 | 커밋 후보에 무관한 변경을 넣지 않음 | [커밋 상태 확인](../skills/preparing-commit/SKILL.md#상태와-변경-확인) |
| 파일 작성 요청과 응답 작성 구분 | 불필요한 저장소 변경을 줄임 | [PR 문서 위치](../skills/pr-documentation/SKILL.md#문서-위치와-언어) |
| 저장소 규칙·기존 관례 우선 | 특정 프로젝트의 폴더·언어를 전체에 강제하지 않음 | [Plan 문서 위치](../skills/task-planning/SKILL.md#문서-위치), [Steps 위치와 언어](../skills/steps-documentation/SKILL.md#문서-위치와-언어) |

## 2. 개선 후보와 우선순위

우선순위는 분석자의 제안이며 구현 순서에 대한 사용자 결정이 아니다.

| 우선순위 | 개선 후보 | 해결하려는 문제 | 확인할 시나리오 |
|---|---|---|---|
| P1 | 요청의 완료 지점 구분: 설명·수정·기록·메시지·commit·PR 발행 | 문서 작성만 하고 실행 요청을 완료로 취급하는 공백 | Q01, Q19, Q21, Q23 |
| P1 | 계획이 필요한 조건과 바로 수행할 조건을 짧게 명시 | 같은 요청을 P/I가 다르게 해석하는 경계 | Q02, Q07, Q09, Q10 |
| P1 | 이미 받은 승인과 새로 필요한 선택 구분 | 반복 승인·전체 작업 중단 가능성 | Q08, Q09 |
| P1 | 평가할 스킬 버전과 실제 노출 목록 확인 | 소스 변경 효과와 설치본·다른 스킬 영향을 혼동 | [v2 맥락](03-v2-context.md) |
| P2 | C·S의 유용성/필요성 trigger를 실제 사용 목적에 맞게 조정 | 요청하지 않은 후속 산출물 선택 가능성 | Q12, Q15, Q23 |
| P2 | 작은 요청의 산출물 분량과 검증 비용 축약 | 짧은 작업에도 전체 문서 항목을 펼치는 부담 | Q02, Q03, Q05, Q15 |
| P2 | 변경 위험에 비례한 확인 방법 | 문장 길이·파일 수만으로 위험 판단 | Q04, Q10, Q11 |
| P2 | 여러 산출물을 명시 요청한 경우 인계·완료 추적 | 개별 전문 스킬 사이에서 요청 일부 누락 | Q23 |
| P3 | 반복 규칙의 제한적 공통화 | 동기화 비용과 표현 차이 | [구조적 한계](01-structure-and-flow.md#6-유지보수상-장점과-구조적-한계) |
| P3 | 필요가 입증된 예시·템플릿·검증 도구만 추가 | 패키징·상태 관리 복잡도 증가 | [스킬별 분석](README.md#스킬별-분석) |

시나리오 ID는 [요청별 평가표](02-enforcement-and-request-evaluation.md#4-요청별-예상-동작)를 참조한다.

## 3. 강제 규칙을 다루는 방향

강제 규칙은 “누락하면 실제 문제가 생기는 조건”에 집중하는 편이 적절하다. 예를 들어 실행하지 않은 검증을 성공으로 쓰지 않기, 사용자 변경을 혼입하지 않기, 모르는 근거를 만들어내지 않기는 기존 구성의 핵심 가치다.

반면 모든 요청에 계획 파일, 승인 토큰, 전체 테스트, Steps 파일을 요구하는 방식은 현재 main의 가벼운 경로를 바꾼다. 도입하려면 필요한 위험·요청 유형과 실제 비용을 먼저 확인해야 한다. v2에서 사용했다는 이유만으로 v3의 기본값이 되는 것은 아니다.

문서의 필수 항목과 실제 출력 분량도 구분할 수 있다. 검토할 관점은 유지하되 단순한 수정 결과는 짧게 보고하고, 관련 없는 항목은 생략하는 방식이 후보가 된다. 단계별 전문 스킬을 늘릴지 여부 역시 실제 누락 사례와 반복 호출 비용을 비교해 결정한다.

## 4. 아직 확정되지 않은 사용자 작업 방식

사용자가 “현재 사용하는 방식과 차이가 있다”고 밝혔지만 그 방식의 구체적인 규칙은 이번 요청에 포함되지 않았다. 따라서 아래를 사용자 선호로 가정하지 않았다.

| 결정할 사항 | 가능한 선택지 | 선택이 바꾸는 부분 |
|---|---|---|
| 계획 선행 범위 | 계획 요청 때만 / 영향 큰 변경에도 / 모든 개발 | 일상 작업의 승인·문서 비용 |
| 구현 후 기본 산출물 | 완료 보고 / Steps 추가 / 커밋 후보까지 | 자동 후속 선택의 범위 |
| Git 실행 책임 | 준비 전용 / 명시 요청 시 commit·push·PR까지 | 전문 스킬 경계와 완료 기준 |
| 문서 위치·언어 | 저장소 관례 / 개인 기본 규칙 / 요청별 지정 | 재사용성과 개인 워크플로 일치 |
| v3 배포 형태 | 독립 스킬 / 플러그인 / 단계적 패키징 | 설치·발견·버전 확인 방식 |

v3 설계 시에는 실제 짧은 요청 몇 개와 기대하는 종료 상태를 먼저 대응시키면 된다. 예를 들어 “고쳐줘” 이후 파일 수정·검증까지만 원하는지, “정리해줘”가 응답인지 Steps 파일인지가 description과 인계 규칙을 결정한다.

## 5. 다음 설계가 갖추면 좋은 완료 기준

- Q01~Q24에서 선택할 스킬과 종료 지점을 사전에 설명할 수 있다.
- 작은 수정은 불필요한 파일·후속 스킬·중복 승인 없이 마칠 수 있다.
- 짧지만 영향이 큰 변경은 필요한 검증·미결정 사항을 놓치지 않는다.
- 명시 요청한 복합 산출물이 누락되지 않으며, 권한·도구 한계는 정확히 보고한다.
- 정적 형식 검사 통과와 실제 자연어 요청 처리 성공을 별도 증거로 남긴다.
- 설치된 스킬과 편집 중인 소스의 버전·노출 차이를 확인할 수 있다.

이 기준 역시 제안이다. 이번 분석 결과로 v3의 구조나 승인 정책을 확정하거나 기존 v2를 수정하지 않는다.
