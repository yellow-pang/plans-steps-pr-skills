# task-planning 분석

분석 기준은 `main`과 동일한 `d7c0887`의 [원문](../../skills/task-planning/SKILL.md)이다. 이 문서는 원문을 읽은 정적 분석이며, 실제 모델의 스킬 선택률·승인 준수율을 측정한 결과가 아니다. 아래의 강제성은 프롬프트 지침의 강도를 뜻한다. 이 스킬 파일 자체에는 명령 실행을 막는 자동 gate가 없다.

## 역할과 선택 조건

`task-planning`은 구현 전에 조사·범위·대안·검증 방법을 정리하는 계획 전용 스킬이다. description은 ① 사용자가 구현 계획을 요청한 경우와 ② 구현 전에 범위·대안·승인 사항을 결정해야 하는 경우를 포함한다. 명시적인 “계획을 작성해 줘”뿐 아니라 모호하거나 선택이 필요한 개발 요청도 선택 대상이 된다. [근거: frontmatter 및 핵심 원칙](../../skills/task-planning/SKILL.md#핵심-원칙), 원문 1~10행.

두 번째 조건의 “결정해야 하는 경우”에는 규모나 위험 기준이 없다. 따라서 어떤 불확실성을 모델이 자체 조사로 해결하고 어떤 것을 계획·승인으로 넘길지는 판단에 맡겨져 있다. 단순 수정에서 반드시 거쳐야 하는 진입 스킬이라는 규칙은 없다.

## 입력·산출물·책임 범위

| 구분 | 원문에서 확인되는 내용 |
| --- | --- |
| 입력 | 사용자 요구, 적용되는 저장소 지침, 현재 브랜치와 기존 변경, 코드·진입점·계약·설정·테스트·문서 |
| 선택 입력 | 현재 작업과 관련된 Steps·Commit·PR 자료. 없다고 중단하지 않음 |
| 산출물 | 조사 근거를 갖춘 구현 계획, 추천 대안, 가정·결정 필요 사항·후속 작업 |
| 응답과 파일 | 계획 내용만 요청하면 응답으로 제공. 계획 파일 작성을 요청했을 때만 저장소 문서 생성·수정 |
| 파일 위치 | 저장소 지침 → 기존 문서 구조·명명 규칙 → `docs/plans/`. 다른 산출물과 번호·파일명 강제 동기화 없음 |
| 기본 책임 밖 | 구현, staging, commit, push, PR 생성, 커밋 메시지 후보 작성 |

근거: [사전 확인](../../skills/task-planning/SKILL.md#사전-확인), [문서 위치](../../skills/task-planning/SKILL.md#문서-위치), [승인 대기](../../skills/task-planning/SKILL.md#승인-대기). 기본 책임 밖이라는 선언은 이 스킬의 동작 경계이며, 상위 지침과 사용자 권한을 처리하는 별도 실행 장치가 있다는 의미는 아니다.

## 처리 흐름

1. 적용되는 `AGENTS.md`, `CONTRIBUTING.md` 등을 읽고 현재 브랜치와 기존 변경을 확인한다. 사용자 변경과 예상 작업 범위를 분리한다.
2. 관련 구현·진입점·계약·설정·테스트·문서를 조사한다. manifest, 테스트·빌드 설정, CI에서 실제 검증 방법을 찾는다.
3. 문서와 구현이 다르면 코드·설정·테스트·Git diff를 우선하고 불일치를 기록한다.
4. 작업 범위, 제외 범위, 사용자 승인·선택이 필요한 범위, 별도 후속 작업을 나눈다.
5. 대안이 둘 이상이면 일관성·변경 범위·호환성·유지보수성·검증 가능성·배포 영향·위험을 비교하고 추천 근거를 제시한다. 미확인 내용은 가정 또는 결정 필요 사항으로 표시한다.
6. 요청에 따라 응답 또는 계획 파일을 작성한다. 파일을 요청한 경우에만 문서 위치 규칙을 적용한다.
7. 사용자에게 계획을 제시한 뒤 승인·대안 선택·수정·취소를 명시할 때까지 대기한다. 다음 구현 단계로 자동 진행하지 않는다.

근거: [핵심 원칙](../../skills/task-planning/SKILL.md#핵심-원칙)부터 [승인 대기](../../skills/task-planning/SKILL.md#승인-대기)까지.

계획에는 문제·현재 상태, 조사 근거, 범위, 대안·결정, 예상 변경 파일·주요 인터페이스, 구현 단계·선후관계, 계약 또는 실행 흐름, 위험, 완료 조건, 검증 방법, 결정 필요 사항·후속 작업이 들어간다. 각 단계는 독립적으로 검증할 수 있어야 한다. 배포나 데이터 변경이 있을 때에는 마이그레이션·롤백·관측 방법도 추가한다. [근거: 계획 내용](../../skills/task-planning/SKILL.md#계획-내용), 원문 45행.

## 강제성 평가

| 강도 | 규칙 | 효과와 한계 |
| --- | --- | --- |
| 명시적 금지·대기 | 계획 승인 전 구현 금지, 계획 제시 후 명시적 사용자 응답까지 대기 | 성급한 구현을 억제하는 문구가 분명함. 실제 승인 상태를 저장·검증하는 기능은 없음 |
| 명시적 금지 | staging·commit·push·PR 생성·커밋 메시지 후보 작성 금지 | 계획과 Git 작업의 책임 분리. 복합 요청을 다른 스킬로 넘기는 절차는 없음 |
| 필수 절차 | 저장소 지침·Git 상태·실제 코드와 검증 설정 조사 | 근거 없는 계획을 줄임. 아주 작은 계획 요청에도 조사 깊이 축약 기준은 없음 |
| 필수 내용 | 계획의 구성 항목과 단계별 검증 가능성 | 계획의 누락을 줄임. 작업 크기에 따른 생략·요약 허용 규칙은 없음 |
| 조건부 필수 | 대안이 복수이면 비교, 배포·데이터 변경이면 운영 대응 포함 | 조건은 있으나 복수 대안을 반드시 만들어야 한다는 요구는 아님 |
| 조건부 허용 | 사용자가 계획 파일 작성을 요청한 경우에만 파일 수정 | “계획을 알려 줘”를 저장소 변경으로 확대하지 않음 |
| 모델 판단 | 승인 필요 범위, 조사 깊이, 대안의 적용 가능성, 위험 판단 | 명시적 위험 등급이나 의사결정 기준이 없어 일관성은 모델에 의존 |

원문에는 “권장” 수준으로만 선언한 별도 규칙이 거의 없다. 조사·구성·금지 사항을 직접 지시하는 반면, 그 적용 규모는 모델 판단으로 남겨 둔다. [근거: 사전 확인](../../skills/task-planning/SKILL.md#사전-확인), [범위와 대안](../../skills/task-planning/SKILL.md#범위와-대안), [계획 내용](../../skills/task-planning/SKILL.md#계획-내용).

## 간단한 요청을 어떻게 처리할 것으로 예상되는가

아래는 description과 본문에 근거한 예상 경로다. 실제 호출 여부를 시험한 결과가 아니다.

| 요청 예시 | 예상 선택·동작 | 근거와 인식 한계 |
| --- | --- | --- |
| “이 오류 수정 계획만 알려 줘” | 선택 가능성이 높음. 조사 후 응답으로 계획 제공, 구현하지 않음 | description의 명시적 계획 요청 + 파일 요청 조건 + 승인 대기와 직접 일치 |
| “로그인 개선 계획을 파일로 만들어 줘” | 선택 가능성이 높음. 지침·관례에 맞는 계획 파일 작성 후 대기 | 파일 생성 권한과 위치 규칙이 명확함. “개선” 범위는 조사·결정 필요 사항으로 남을 수 있음 |
| “버튼 문구 오타 고쳐 줘” | 이 스킬보다 `implementation-workflow`가 자연스러운 후보 | 계획 요청도 미결정 범위도 없는 경우라는 추론. 단순 변경 제외 예시가 없어 오선택 가능성은 남음 |
| “인증을 개선해 줘” | 범위·대안 결정이 필요하다고 판단하면 선택 | 두 번째 description 조건이 유효하지만, 어떤 질문을 먼저 할지와 계획 작성 시점은 정해져 있지 않음 |
| “계획 세우고 바로 구현해 줘” | 기본 스킬 문구는 계획 이후 승인 대기를 요구함 | 동일 요청이 구현 권한까지 부여한 경우의 처리 규칙이 없어 경계가 모호함. 실제 처리는 상위 지침·사용자 권한 해석에 좌우됨 |

선택 조건은 짧은 자연어 계획 요청을 잘 포괄하도록 쓰여 있다. 반면 간단한 요청에 대한 **답변 분량과 조사 비용을 줄이는 규칙은 약하다**. “간단히 계획만”이라고 요청해도 전체 계획 구성 항목을 어느 정도로 압축할지는 별도 정의가 없다.

## 다른 스킬과의 경계 및 충돌 가능성

- **구현과의 경계:** 이 스킬은 계획·승인 대기까지 맡는다. [implementation-workflow의 핵심 원칙](../../skills/implementation-workflow/SKILL.md#핵심-원칙)은 승인된 계획이 없더라도 명확한 사용자 요청을 기준으로 구현하도록 한다. 전체 흐름이 반드시 계획부터 시작하는 직렬 절차는 아니다.
- **선택 경계:** “구현 전에 결정이 필요함”과 “계획 없이도 범위가 명확함”을 가르는 공통 기준이 없다. 같은 요청이 모델 판단에 따라 두 스킬 중 어느 쪽으로도 들어갈 수 있다.
- **후속 문서와의 경계:** 관련 Steps·Commit·PR 자료는 있을 때만 참고한다. 계획 작성이 후속 문서 생성이나 동일 번호 사용을 요구하지 않는다.
- **커밋과의 경계:** 메시지 후보는 `preparing-commit` 책임이라고 명시하지만 자동 호출·위임 방법은 없다. 계획과 커밋을 동시에 요청할 때의 조정 규칙도 별도로 정의하지 않는다.
- **승인 경계:** 사용자 승인·대안 선택을 기다린다는 문구는 분명하지만, 승인 대상·승인된 범위의 표현 형식과 이후 범위 변경 시 재승인 규칙은 이 파일에 없다. 기존 세션의 승인을 재사용하는 조건이나 매 요청마다 새 승인을 받아야 하는지도 상세하게 정의하지 않는다.

## 유지할 가치와 v3 개선 후보

| 구분 | 내용 |
| --- | --- |
| 유지 | 코드·설정·테스트·diff 우선, 관련 문서 부재 허용, 사실과 가정 구분 |
| 유지 | 응답과 파일 생성의 분리, 저장소 관례 존중, 문서 번호 강제 연결 없음 |
| 유지 | 대안 비교와 검증 가능한 계획 단계, 계획 단계에서 Git 게시 작업 분리 |
| 개선 후보 | “단순하고 명확한 수정”, “조사로 해결 가능한 불확실성”, “사용자 결정이 필요한 변경”을 나누는 공통 선택 규칙 |
| 개선 후보 | 짧은 계획·보통 계획·복잡한 계획의 필요한 항목과 깊이를 구분하는 규모별 작성 규칙 |
| 개선 후보 | 이미 승인된 요청, “계획 후 바로 구현” 같은 복합 요청, 수정된 계획에 대한 권한 처리 명시 |
| 개선 후보 | 승인 대상과 남은 결정 사항을 간결하게 표시하고, 후속 구현이 읽을 수 있는 인계 형식 정의 |

개선 후보는 현재 원문에 없는 설계 제안이며, 이번 분석에서 구현한 기능이 아니다. v3에서는 위 예시를 실제 선택·출력 평가에 사용해 오선택, 불필요한 승인 대기, 과도한 계획 분량을 확인할 수 있다.
