# implementation-workflow 분석

분석 기준은 `main`과 동일한 `d7c0887`의 [원문](../../skills/implementation-workflow/SKILL.md)이다. 이 문서는 원문을 읽은 정적 분석이며, 실제 모델의 스킬 선택률·수정 성공률을 측정한 결과가 아니다. 강제성은 프롬프트 지침의 강도를 뜻하고, 이 스킬 파일 자체에 명령 실행을 차단하는 자동 gate는 없다.

## 역할과 선택 조건

`implementation-workflow`는 기능 구현, 버그 수정, 테스트 추가, 리팩터링, 문서와 구현의 불일치 수정을 수행하는 스킬이다. description은 ① 승인된 계획을 구현하는 요청과 ② 계획 없이도 범위가 명확한 변경 요청을 모두 받는다. 즉 계획 파일이나 승인 절차를 모든 구현의 선행 조건으로 만들지 않는다. [근거: frontmatter 및 핵심 원칙](../../skills/implementation-workflow/SKILL.md#핵심-원칙), 원문 1~10행.

“고쳐 줘”, “추가해 줘”, “이 계획대로 구현해 줘”처럼 짧은 개발 요청에 대응할 범위가 넓다. 다만 “범위가 명확함”의 기준과 단순 수정·복잡한 변경을 구분하는 기준은 정의되지 않았다. 순수한 설명 요청이나 일반 문서 작성 요청은 description의 명시적 대상이 아니다.

| --- | --- |

| 입력 | 저장소 지침, 현재 브랜치와 기존 변경, 범위·제외 범위·대상 파일·완료 조건 |
| 조사 근거 | 현재 코드·설정·테스트·Git diff, manifest·테스트·빌드·CI 설정 |

| 문서·후속 스킬 | 명시적으로 요청하지 않은 문서 생성이나 후속 스킬 실행을 강제하지 않음 |
| 기본 책임 밖 | `git add`, commit, push, PR 생성, 커밋 메시지 후보 작성 |

근거: [핵심 원칙](../../skills/implementation-workflow/SKILL.md#핵심-원칙), [사전 확인](../../skills/implementation-workflow/SKILL.md#사전-확인), [검증과 완료 확인](../../skills/implementation-workflow/SKILL.md#검증과-완료-확인), [금지 사항](../../skills/implementation-workflow/SKILL.md#금지-사항). Git 작업 금지는 이 스킬의 기본 책임 경계이며, 실제 세션의 상위 지침과 사용자 권한까지 처리하는 실행 장치라는 뜻은 아니다.

## 처리 흐름

1. 저장소 지침, 브랜치, 기존 변경을 확인하고 범위·제외 범위·대상 파일·완료 조건을 정리한다.
2. 관련 계획·문서가 있으면 현재 구현과 비교한다. 차이가 있으면 코드·설정·테스트·Git diff를 우선한다.
3. manifest, 테스트·빌드 설정, CI에서 사용할 검증 명령을 확인한다. 승인 필요 범위가 남아 있으면 그 부분은 구현하지 않는다.
4. 기존 패턴·사용자 변경을 보존하며 최소 변경으로 해결한다. 관련 없는 정리·추상화를 섞지 않는다.
5. 구조 변경과 동작 변경은 독립적으로 검증 가능한 단계로 나눈다. 복잡한 작업도 검증 가능한 단계로 나눈다.
6. 범위 밖 변경이 필요하면 이유·대상·영향·위험을 먼저 보고하고, 명시적 승인 전까지 해당 변경을 중단한다.
7. 계약 변경은 producer·consumer·타입·오류 처리·문서·테스트를 함께 확인한다.
8. 각 단계에서 관련 검증과 diff를 확인하고 실패 원인을 구분한다. 완료 전에 `git status`와 `git diff`로 변경 전체를 점검한다.
9. 실제 실행한 검증만 근거로 최종 보고한다. 커밋 준비나 PR 작업으로 자동 넘어가지 않는다.

근거: [사전 확인](../../skills/implementation-workflow/SKILL.md#사전-확인)부터 [금지 사항](../../skills/implementation-workflow/SKILL.md#금지-사항)까지.

버그 수정에는 별도 순서가 있다. **증상·재현 조건 확인 → 원인 추적 → 가능한 회귀 테스트 → 최소 수정 → 회귀 검증**으로 진행하며, 오류를 숨기는 우회책을 해결로 보지 않는다. “가능한 회귀 테스트”라는 표현이므로 모든 수정에서 새 테스트 파일을 반드시 만들어야 한다는 규칙은 아니다. [근거: 구현](../../skills/implementation-workflow/SKILL.md#구현), 원문 30행.

완료 검토는 범위 밖 변경, 임시 파일, 비밀값, 불필요한 포맷 변경, 누락된 문서를 확인한다. 실패 보고는 이번 변경으로 생긴 실패, 기존 실패, 환경·외부 의존성 때문에 실행하지 못한 검증으로 구분한다. [근거: 검증과 완료 확인](../../skills/implementation-workflow/SKILL.md#검증과-완료-확인), 원문 34~41행.

## 강제성 평가

| 강도 | 규칙 | 효과와 한계 |
| --- | --- | --- |
| 필수 작업 기준 | 승인된 계획 또는 명확한 사용자 요청을 따름 | 문서 없는 간단한 작업도 진행 가능. 계획과 최신 요청이 충돌할 때의 우선순위는 명시하지 않음 |
| 명시적 부분 중단 | 승인 필요 범위 또는 요청 밖 변경은 승인 전 구현하지 않음 | 해당 부분만 중단하는 문구라 독립적인 나머지 작업까지 멈추라는 요구는 아님 |
| 필수 구현 원칙 | 사용자 변경 보존, 최소 변경, 무관한 정리 금지 | 범위 통제에 유효. 최소 변경과 계약 전체 수정의 적정선은 판단 필요 |
| 조건부 필수 | 복잡한 작업의 단계 분할, 계약 변경의 관련 요소 확인, 버그 수정 순서 | 상황별 절차가 있음. 복잡도나 계약 영향 판정 기준은 없음 |
| 필수 검증·보고 | 각 단계 검증·diff 확인, 최종 상태 점검, 실제 실행 근거만 보고 | 완료 판단 근거가 분명함. 변경 규모별 적정 검증량·중단 조건은 없음 |
| 강제하지 않음 | 요청하지 않은 문서 생성·후속 스킬 실행 | 자동 문서 연쇄 작업을 줄임. 관련 기술 문서 수정과 별도 기록 문서 생성의 구분은 더 명확히 할 수 있음 |
| 명시적 금지 | `git add`·commit·push·PR 생성·커밋 메시지 후보 작성 | 구현과 Git 게시 책임을 분리. 직접적인 커밋 요청의 인계 절차는 없음 |
| 모델 판단 | 범위 명확성, 승인 필요성, 복잡도, 가능한 회귀 테스트, 적절한 검증 | 유연하지만 동일 요청에 대한 재현성은 모델에 의존 |

원문은 “권장” 중심의 안내가 아니라 명령형 절차와 금지 사항으로 구성된다. 그러나 “가능한”, “관련”, “복잡한” 등의 적용 판단은 모델에 남아 있어 강한 문구만으로 항상 같은 동작을 보장하지 않는다.

## 간단한 요청을 어떻게 처리할 것으로 예상되는가

아래는 description과 본문으로 예상한 경로이며, 실제 호출·구현 평가 결과가 아니다.

| 요청 예시 | 예상 선택·동작 | 근거와 인식 한계 |
| --- | --- | --- |
| “저장 버튼 문구를 ‘완료’로 바꿔 줘” | 범위가 명확하면 계획 없이 직접 수정 가능 | 명확한 요청을 작업 기준으로 허용. 간단한 문구 수정의 검증 깊이는 별도 규칙 없음 |
| “빈 입력에서 오류가 나니 고쳐 줘” | 버그 수정 경로로 진입해 재현·원인 확인 후 최소 수정 | description과 버그 절차가 직접 대응. 재현이 안 될 때 중단·추가 질문 기준은 없음 |
| “이 함수에 테스트 추가해 줘” | 테스트 추가 작업으로 선택 가능 | description에 테스트 추가가 명시됨. 구체적 대상 함수·요구 동작은 코드에서 확인 필요 |
| “문서와 실제 옵션명이 다르니 맞춰 줘” | 문서·구현 불일치 수정으로 선택 가능 | 불일치 수정이 명시됨. 실제 구현 우선 원칙이 있지만 구현 자체가 결함인지 판단할 근거는 조사해야 함 |
| “이 버그 고치고 커밋까지 해 줘” | 수정 부분은 담당하지만 기본 스킬 경계는 커밋을 제외 | 본문은 커밋을 금지하고 메시지 후보는 다른 스킬 책임으로 둠. 실제 사용자 권한을 반영한 복합 요청 분기·인계 규칙은 없음 |

단순 개발 요청을 직접 받는 데에는 다섯 스킬 중 핵심 역할을 한다. 계획 문서 부재로 멈추지 않고 후속 문서를 강제하지 않는 점이 적합하다. 다만 아주 작은 작업에서도 사전 확인·범위 정리·단계 검증·최종 보고를 얼마나 압축할지 정의하지 않아 절차 과잉 가능성이 있다.

## 다른 스킬과의 경계 및 충돌 가능성

- **계획과의 경계:** [task-planning의 선택 조건과 승인 대기](../../skills/task-planning/SKILL.md#승인-대기)는 결정이 필요한 요청을 계획으로 보낸다. 이 스킬은 명확한 요청을 직접 구현한다. 공통된 명확성·위험 기준이 없어 초기 선택이 흔들릴 수 있다.
- **Steps와의 경계:** 최종 응답에는 변경·검증·위험을 포함하지만 별도 Steps 파일 작성은 강제하지 않는다. [steps-documentation](../../skills/steps-documentation/SKILL.md#문서-위치와-언어)은 파일 작성 요청이 있을 때 기록 문서를 만든다.
- **문서 수정의 경계:** 계약 변경 시 문서를 확인하고 완료 시 누락된 문서를 점검하는 규칙과, 요청하지 않은 문서 생성을 강제하지 않는 규칙이 함께 있다. 기존 기술 문서의 필수 동기화와 새 작업 기록 파일의 생성을 구분하면 해석이 쉬워진다.
- **커밋과의 경계:** 커밋 메시지 후보는 [preparing-commit](../../skills/preparing-commit/SKILL.md#핵심-원칙)의 책임이다. 구현 완료를 이유로 그 스킬 실행을 강제하지 않는다. 실제 커밋 실행 절차도 이 파일에 없다.
- **PR과의 경계:** 변경 보고가 PR 설명을 자동 생성하지 않는다. [pr-documentation](../../skills/pr-documentation/SKILL.md#핵심-원칙)은 별도 설명 작성 역할이며 실제 PR 생성도 하지 않는다.

## 유지할 가치와 v3 개선 후보

2026-09-27에 추가된 사용자 개발 요구와 후속 구체 설계를 반영해 아래 **v3 제안만** 갱신했다. 위의 원문·흐름·강제성 평가는 `d7c0887` 기준으로 유지한다. 구현할 책임·판단 기준은 [v3 구체 설계](../04-v3-upgrade-considerations.md)에 있다.

| 구분 | 내용 |
| --- | --- |
| 유지 | 승인된 계획과 직접 구현 요청을 모두 허용하고 관련 문서 부재로 멈추지 않는 진입 구조 |
| 유지 | 사용자 변경 보존, 무관한 변경 배제, 승인 필요 범위만 부분 중단하는 경계 |
| 추천 설계 | `최소 변경/최소 수정`을 영향 해결 기준으로 대체. 분석은 관련 lifecycle과 영향 종료 근거까지, 수정은 확인된 요구·영향을 해결하는 만큼 수행하고 무관한 변경은 배제 |
| 유지 | 버그의 원인·재현·회귀 검증, 계약 변경의 관련 요소 확인 |
| 유지 | 변경 유발 실패·기존 실패·미실행 검증 구분, 실제 수행 근거에 한정한 보고 |
| 개선 후보 | 계획 필요 여부·위험·복잡도에 대한 스킬 공통 분기 기준과 짧은 요청 예시 |
| 개선 후보 | 작은 수정에서 범위 정리·검증·보고를 압축하는 규칙과 검증 충분성 기준 |
| 개선 후보 | 기존 계획과 최신 사용자 지시의 관계, 이미 받은 승인 범위, 복합 요청의 단계별 권한 처리 |
| 개선 후보 | 필요한 기술 문서 동기화와 선택적인 Plans·Steps·PR 기록 파일 생성의 경계 명시 |
| 개선 후보 | 재현 불가·테스트 실패·환경 제약에서 계속할 수 있는 작업과 확인이 필요한 작업의 구분 |
| 개선 후보 | 외부 동작 관측 후 fixture·계약 판단, 기존 테스트의 유효성 판단, 유효한 검증 근거 재사용 |

개선 후보는 현재 원문에 없는 설계 제안이며, 이번 분석에서 구현한 기능이 아니다. v3 평가는 짧은 수정 요청의 직접 구현 여부, 불필요한 문서·승인 대기 여부, 범위 밖 변경의 억제 여부를 나누어 실제 동작으로 확인하는 것이 적절하다.
