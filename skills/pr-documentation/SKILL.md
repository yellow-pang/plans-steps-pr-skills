# PR Documentation

## 핵심 원칙

현재 변경의 실제 코드, 설정, 테스트 결과와 Git diff를 기준으로 리뷰어용 설명을 작성합니다. Plans나 Steps가 없어도 진행하며 실제 Pull Request는 생성하지 않습니다.

## 사전 확인

1. 적용되는 저장소 지침과 기존 PR 형식을 확인합니다.
2. 기준 브랜치와 비교할 수 있으면 커밋된 변경까지 포함한 전체 PR diff를 확인하고, working tree의 staged, unstaged, untracked 변경은 별도로 구분합니다.
3. 변경 파일, 계약, 설정, 테스트와 알려진 제한을 확인합니다.
4. 관련 Plan이나 Steps가 있으면 실제 변경과 대조합니다.

기존 사용자 변경이나 관련성이 불명확한 변경을 하나의 PR 범위로 추정하지 않습니다. 기준 브랜치나 변경 범위를 확인할 수 없으면 확인 가능한 범위만으로 초안을 작성하고 그 한계를 명시합니다.

## 문서 위치와 언어

위치와 이름은 다음 순서로 결정합니다.

1. 저장소 지침에 명시된 규칙
2. 저장소에서 이미 사용하는 문서 구조와 이름 규칙
3. 규칙이 없으면 `docs/pr/`

다른 문서와 번호나 파일명을 강제로 맞추지 않습니다. 문서 언어는 사용자 요청을 우선하고, 요청이 없으면 저장소의 기존 PR 또는 문서 언어를 따릅니다.

사용자가 파일 작성을 요청했을 때만 저장소에 문서를 생성하거나 수정합니다. PR 설명만 요청한 경우에는 응답으로 제공합니다.

## 문서 내용

- 변경 배경과 목적
- 주요 변경과 사용자 또는 시스템 영향
- 영향받는 범위와 영향받지 않는 범위
- 계약, 데이터 또는 실행 흐름
- 주요 변경 파일
- 실행 기록으로 확인한 검증과 결과
- 리뷰 시 집중할 부분
- 알려진 제한, 배포 고려사항과 후속 작업

관련 Plans, Steps, Commit 자료는 존재하고 현재 변경과 관련될 때만 연결합니다. diff에 없는 효과나 성능 개선을 주장하지 않습니다.
테스트 파일이나 CI 설정의 존재를 테스트 통과로 표현하지 않으며, 영향받지 않는 범위는 근거로 확인할 수 있을 때만 작성합니다.

## 금지 사항

실행하지 않은 검증을 성공으로 기록하거나 무관한 변경을 포함하지 않습니다. `git add`, commit, push, PR 생성, reviewer 지정, merge는 수행하지 않으며 커밋 메시지도 생성하지 않습니다.
