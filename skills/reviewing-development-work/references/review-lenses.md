# 대상별 검토 관점

## 분석

원래 요구와 현재 코드/runtime 근거를 비교한다. producer·consumer, 상태 전이, 비동기·외부 경계, 오류 경로에서 누락된 영향이 있는지 본다. 관측과 가정, 실제 계약과 오래된 fixture를 구별한다. 영향이 닫혔다는 주장에는 근거가 필요하다.

## Plan

요구에 맞는 완료 조건과 변경 범위인가. lifecycle/계약 변경과 실제 관측이 빠지지 않았는가. 같은 parser 실패를 여러 층에서 반복 검사하거나 이미 보호된 실패만 새 테스트로 추가하지 않는가. 고유 DB 저장 검사처럼 다른 failure mode를 지키는 검증은 보존한다. 중복 validation·state·metadata, 불필요한 abstraction, coupling과 유지보수·확장성 문제를 본다. 파일·class·테스트 수 자체로 과설계를 판정하지 않는다. 최소 diff 집착으로 원인 해결을 놓치지 않는가.

중복·복잡도를 줄이자고 제안할 때는 **합치거나 제거할 항목과 유지할 항목을 각각 명시**하고 이유를 설명한다. 같은 parser 실패를 세 계층에서 반복하는 검사와, 실제 DB 저장·재조회라는 별도 실패 경로를 검증하는 검사는 구별한다. 미래 가능성만을 위한 범용 추상화와 현재 외부 응답을 내부 상태로 바꾸는 경계 adapter도 구별한다. 후자의 필요가 코드와 계약으로 확인되면 유지할 근거를 검토 결과에 적는다.

## 구현

실제 변경과 사용자 요구·Plan을 대조한다. 관련 producer/consumer와 기존 서비스 영향, 테스트의 유효성, 검증 결과의 적용성을 확인한다. Steps는 탐색 자료이며 코드·runtime의 증거를 대신하지 않는다. 실행하지 않은 검증이나 미관측 외부 동작을 성공으로 받아들이지 않는다.

검토 범위가 구현 문서나 커밋 준비까지 포함한다면 산출물도 본다. Steps가 대화를 모르는 독자에게 문제·전후 동작·검증 한계를 설명하는가, 중요한 영어 용어가 설명 없이 나열되지 않는가, 커밋 제목·본문이 현재 대상의 주요 변경을 빠짐없이 담는가를 확인한다. 단순히 글이 짧거나 표가 없다는 이유로 결함으로 판정하지 않는다.
