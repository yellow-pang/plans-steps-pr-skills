# 테스트와 검증 판단

테스트는 현재 유효한 동작을 보호한다. 새 테스트는 가능하면 기존 테스트가 놓치는 중요한 failure mode를 가져야 한다. Unit/Integration/E2E가 같은 계약만 반복하면 중복 후보지만, 서로 다른 경계의 고유 실패를 지키면 유지한다. 파일·기능마다 기계적으로 하나씩 만들지 않는다.

기존 실패의 원인을 현재 요구, 실제 runtime, 확인된 계약과 비교한다. 오래된 테스트·잘못된 mock/fixture·외부 변화·구현 세부 과결합을 확인한 뒤 수정·통합·삭제할 수 있다. 유효한 회귀 보호는 보존하고 변경 근거와 남는 보호 범위를 설명한다. 조회 가능한 Browser/provider 동작을 가짜 fixture보다 우선 관측한다. 합성 오류 재현은 시뮬레이션으로 표시한다.

한 번 `ready`를 관측했다고 `pending`이 잘못된 계약이라고 단정하지 않는다. 작업 진행 중/완료 같은 정상 상태 차이인지, 버전·조건 차이인지 먼저 확인한다. 외부 형태를 확인할 수 없으면 그 정보가 필요한 부분만 보류하고 알려진 내부 계약의 작업은 진행한다.

검증 결과를 재사용할 때는 이후 관련 코드, dependency/config, 환경, 입력과 현재 위험이 동일한지 및 실행 근거가 남았는지 확인한다. SHA만 달라졌다는 이유로 무조건 재실행하지 않고, 같은 SHA라는 이유로 무조건 재사용하지 않는다. 관련 변경이나 새 failure mode가 있으면 영향받는 검사만 다시 수행한다. 기존 실패·이번 회귀·환경 차단을 구분해 보고한다.

필요한 근거는 검사한 대상·명령 또는 관측 방법·결과·관련 코드 상태와 환경이다. 새 기록 시스템을 만들 필요는 없다. 요청된 동작이나 위험이 바뀌어도 기존 증거의 범위를 다시 판단한다. 저장소가 요구하는 필수 검사나 현재 원격 상태 확인을 과거 로컬 통과로 대체하지 않는다.

## 검증 수준을 고르는 예

| 변화 | 확인할 고유 실패와 적절한 증거 후보 |
|---|---|
| 이미 확인한 응답을 해석하는 함수 수정 | 해당 입력의 해석 오류: 함수 단위 검사로 충분할 수 있음 |
| 처리한 값을 DB에 저장하는 방식 변경 | 변환 값과 저장 값의 불일치: 연결 검사 필요 여부 판단 |
| 브라우저 입력부터 저장·화면 표시까지 경로 변경 | 환경·연결의 오류: 실제 흐름을 확인하는 smoke 또는 E2E 검사 고려 |
| 문구·문서만 수정 | 실제 표시·내용·링크 확인으로 충분하면 별도 단위 테스트 생략 |

단위 검사(Unit)는 한 부분, 연결 검사(Integration)는 부분 사이 계약, 전체 흐름 검사(E2E)는 사용자 흐름을 보호한다. 같은 값이 등장해도 잡는 실패가 다르면 중복이 아니다. 모든 계층의 테스트를 항상 만들거나 순서대로 실행하라는 표가 아니다.
