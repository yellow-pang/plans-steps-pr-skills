# Implementation Workflow

## 핵심 원칙

승인된 계획이 있으면 이를 따르고, 없으면 명확한 사용자 요청을 작업 기준으로 사용합니다. 관련 Plans, Steps, Commit, PR 자료의 부재는 구현 중단 사유가 아닙니다.

## 사전 확인

1. 적용되는 저장소 지침과 현재 브랜치, 기존 변경을 확인합니다.
2. 요청 범위, 제외 범위, 대상 파일과 완료 조건을 정리합니다.
3. 계획이나 관련 문서가 있으면 현재 구현과 대조하되, 코드, 설정, 테스트, Git diff를 우선합니다.
4. 실제 manifest, 테스트 설정, 빌드 설정, CI 구성에서 사용할 검증 명령을 확인합니다.

승인이 필요한 범위가 남아 있으면 해당 부분을 구현하지 않습니다.

## 구현

- 기존 패턴과 사용자 변경을 보존합니다.
- 최소 변경으로 요청을 해결하고 관련 없는 정리나 추상화를 섞지 않습니다.
- 구조 변경과 동작 변경은 서로 독립적으로 검증할 수 있는 작업 단계로 나눕니다.
- 복잡한 작업은 검증 가능한 단계로 나눕니다.
- 계획이나 요청 밖 변경이 필요하면 이유, 대상, 영향과 위험을 먼저 보고하고 명시적 승인 전까지 해당 변경을 중단합니다.
- 계약 변경은 관련 producer, consumer, 타입, 오류 처리, 문서와 테스트를 함께 확인합니다.

버그 수정은 증상과 재현 조건 확인, 원인 추적, 가능한 회귀 테스트, 최소 수정, 회귀 검증 순서로 진행합니다. 오류를 숨기는 우회책을 해결로 간주하지 않습니다.

## 검증과 완료 확인

각 단계에서 관련 검증과 diff 확인을 수행합니다. 실패는 다음과 같이 구분합니다.

- 이번 변경으로 발생한 실패
- 기존 실패
- 환경이나 외부 의존성 때문에 실행하지 못한 검증

완료 전 `git status`와 `git diff`로 범위 밖 변경, 임시 파일, 비밀값, 불필요한 포맷 변경과 누락된 문서를 점검합니다. 실제 실행한 검증만 결과로 보고합니다.
최종 보고에는 원인 또는 목적, 실제 변경, 실행한 검증과 결과, 실행하지 못한 검증, 남은 위험을 포함합니다.

## 금지 사항

사용자가 명시적으로 요청하지 않은 문서 생성이나 후속 Skill 실행을 강제하지 않습니다. `git add`, commit, push, PR 생성은 수행하지 않습니다.
커밋 메시지 후보도 작성하지 않으며, 필요한 경우 독립적인 `preparing-commit`이 담당합니다.
