# Implementation Workflow

요청과 이미 승인된 범위, 적용 지침, 현재 branch·기존 사용자 변경을 확인한다. 관련 Plan/Context가 있으면 참고하되 현재 코드·runtime과 다른 핵심 사실은 재확인한다. 계획이 없다는 이유만으로 명확한 작업을 중단하지 않는다.

**분석은 필요한 만큼 넓게 하고, 확인된 영향을 해결할 만큼 수정한다.** 데이터·상태·API·DB·worker·async·Browser/provider·UI 등의 경계를 통과할 때 관련 producer/consumer, 상태 전이, 오류 경로를 추적한다. 영향이 닫힌 근거가 있으면 조사를 멈춘다. 무관 변경은 배제하되 최소 diff 때문에 원인을 남기지 않는다. 사용자 기존 변경을 덮어쓰거나 혼입하지 않는다.

외부 동작을 실제로 조회할 수 있으면 관측하고 의미·안정성을 판단한 뒤 구현·테스트 계약에 반영한다. 관측 전 예상 payload·DOM·metadata를 임의 fixture로 고정하지 않는다. 내부 로직이나 확인된 계약의 mock은 사용할 수 있다. 기존 테스트 실패는 regression, 오래된 기대값, 요구 변경, 잘못된 fixture, 외부 변화, 구현 세부 결합을 구분한다. 유효 테스트를 단지 통과를 위해 지우지 않는다. 상세 판단은 [검증 기준](references/verification.md)을 필요한 때 읽는다.

Plan과 다른 사실을 발견하면 근거를 따라 구현 세부를 조정한다. 제품 의미·데이터 계약·외부 영향이나 승인 범위를 실질적으로 바꿔야 하면 해당 선택만 확인한다. 검증은 현재 변경과 위험에 필요한 증거를 확보한다. 관련 내용·환경이 그대로이고 기존 실행 근거가 유효하면 재사용할 수 있다. 변경 후 diff·status를 확인하고 실제 수정, 검증 결과, 한계와 남은 위험을 보고한다. 실행하지 않은 검증은 성공이라 쓰지 않는다.

Context는 긴 작업에서 중요한 새 사실·결정이 바뀔 때만 갱신한다. Steps·독립 Review·commit·push·PR은 요청 범위에 있을 때 연결한다. 명확한 작은 작업에 파일 생성이나 후속 단계를 강제하지 않는다.
