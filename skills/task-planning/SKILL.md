# Task Planning

Plan은 **무엇을 할지**를 정한다. 적용 지침, 사용자 요구, 현재 코드·설정·테스트·Git 상태와 관련 분석/Context를 필요한 만큼 확인한다. 독립 분석을 매번 반복하지 않고 중요한 현재 사실을 재확인한다. 조사로 불확실성을 해소할 수 있으면 불필요한 사용자 선택으로 넘기지 않는다.

문제, 범위, 완료 조건, 구현 단계와 선후관계, 영향받는 계약·producer/consumer, 검증 전략을 작업 규모에 맞게 구체화한다. 대안이 실제로 있으면 호환성·유지보수성·coupling·중복·확장성·성능/IO 비용과 검증 가능성을 비교한다. 새 abstraction은 해결할 현재 문제나 합리적인 변화가 설명되어야 한다. 관측하지 않은 외부 값은 가정으로 남기고 계약으로 고정하지 않는다. 테스트는 변경의 고유 실패를 보호하는지 검토하고 오래된 기대값을 무조건 보존할 대상으로 삼지 않는다. 모든 관점을 형식적인 긴 목록으로 출력하지 않는다.

사용자 선택이 필요한 제품 의미·데이터 계약·외부 영향은 선택지와 영향을 분명히 한다. 구현이 가능한 부분과 미결정 부분을 구분한다. Plan을 실제 완료로 표현하지 않는다. Plan만 요청받았다면 그 산출물에서 끝내고, 이미 구현까지 요청됐으며 중요한 선택이 해결됐다면 같은 권한을 다시 묻지 않고 이어간다. 별도 Review를 자동 승인 gate로 만들지 않는다.

파일 요청이면 사용자 지정 위치 → 저장소 관례 → `docs/plans/`를 따른다. 응답만 요청됐다면 파일을 만들지 않는다. Context가 필요한 긴 작업에서는 핵심 결정·미확정만 갱신한다.
