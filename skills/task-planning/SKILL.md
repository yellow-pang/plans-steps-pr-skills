# Task Planning

## 핵심 원칙

실제 코드, 설정, 테스트, Git 상태를 조사하여 구현 가능한 계획을 작성합니다. 관련 문서가 없다는 이유로 중단하지 않으며, 계획 승인 전에는 구현하지 않습니다.

## 사전 확인

1. 작업 경로에 적용되는 `AGENTS.md`, `CONTRIBUTING.md` 등의 지침을 확인합니다.
2. 현재 브랜치와 기존 변경을 확인하여 사용자 변경과 예상 작업 범위를 구분합니다.
3. 관련 코드, 진입점, 계약, 설정, 테스트, 문서를 조사합니다.
4. 실제 manifest, 테스트 설정, 빌드 설정과 CI 구성에서 검증 방법을 확인합니다.
5. 문서와 구현이 다르면 코드, 설정, 테스트, Git diff를 우선하고 차이를 기록합니다.

## 범위와 대안

다음을 구분합니다.

- 작업 범위
- 작업 제외 범위
- 사용자 승인이나 선택이 필요한 범위
- 별도 후속 작업

대안이 둘 이상이면 일관성, 변경 범위, 호환성, 유지보수성, 검증 가능성, 배포 영향, 위험을 비교하고 추천 방향과 근거를 명시합니다. 확인하지 못한 내용은 사실이 아니라 가정 또는 결정 필요 사항으로 표시합니다.

## 문서 위치

다음 순서로 위치와 이름을 결정합니다.

1. 저장소 지침에 명시된 규칙
2. 저장소에서 이미 사용하는 문서 구조와 이름 규칙
3. 규칙이 없으면 `docs/plans/`

다른 문서와 번호나 파일명을 강제로 맞추지 않습니다. 관련 Steps, Commit, PR 자료는 존재하고 현재 작업과 관련될 때만 참고합니다.

사용자가 계획 파일 작성을 요청했을 때만 저장소에 문서를 생성하거나 수정합니다. 계획 내용만 요청한 경우에는 응답으로 제공합니다.

## 계획 내용

계획에는 문제와 현재 상태, 조사 근거, 범위, 적용 가능한 대안과 결정, 예상 변경 파일과 주요 인터페이스, 단계별 구현과 선후관계, 계약 또는 실행 흐름, 위험, 완료 조건, 검증 방법, 결정 필요 사항과 후속 작업을 포함합니다. 배포나 데이터 변경이 있으면 마이그레이션, 롤백과 관측 방법도 다룹니다. 각 단계는 독립적으로 검증 가능한 단위로 작성합니다.

## 승인 대기

계획을 작성한 뒤 구현, staging, commit, push, PR 생성은 수행하지 않습니다. 사용자가 계획 승인, 대안 선택, 수정 또는 취소를 명시할 때까지 기다립니다.
커밋 메시지 후보도 작성하지 않으며, 해당 책임은 `preparing-commit`에 둡니다.
