# Steps Documentation

## 근거와 작성 범위

문서를 읽을 사람은 이전 대화와 전체 diff를 모른다고 가정한다. 요청된 기록 범위를 먼저 확인하고, 그 범위의 실제 코드·설정·커밋된 변경·미커밋 diff·새 파일과 실행 근거를 대조한다. 최근 수정 하나만 전체 작업으로 요약하지 않는다. Plan·Context는 배경 자료이며 완료 사실을 대신하지 않는다. 사용자 기존 변경과 기록 대상을 구분하고 수행하지 않은 검증·확인하지 않은 이유를 사후 창작하지 않는다.

## 이해할 수 있는 설명

사용자 지정 언어를 우선하고 지정이 없으면 한국어로 작성한다. 코드 식별자는 그대로 두되 중요한 전문 용어는 첫 등장에 쉬운 설명을 붙인다. 예를 들어 worker는 “백그라운드 작업 처리기”, lifecycle은 “입력부터 저장·표시까지의 처리 흐름”처럼 해당 작업의 의미로 풀어 쓴다.

배경과 사용자가 겪던 문제 → 원인 → 실제 변경과 선택 이유 → 전후 동작·영향 → 검증·제한을 독자가 연결할 수 있게 쓴다. 필요하면 짧은 예시나 주석, 비교 표, 흐름도를 사용한다. 작은 변경은 짧아도 되지만 여러 계층을 바꾼 작업을 용어 목록 몇 줄로 압축하지 않는다. 분량 자체보다 독자가 무엇이 왜 어떻게 달라졌는지 설명할 수 있는지가 기준이다.

여러 변경이나 데이터·상태 흐름을 설명할 때는 [Steps 작성 기준과 예시](references/writing-guide.md)를 읽는다. Plan과 다른 결과는 확인된 이유와 함께 적고, 부분 완료·미실행 검증·남은 위험을 완료 사실과 구별한다. 제출 전 실제 변경의 주요 목적이 빠지지 않았는지, 근거 없는 효과가 추가되지 않았는지 다시 대조한다.

## 산출물과 종료

파일 위치는 사용자 지정 → 저장소 관례 → `docs/steps/` 순서다. 내용만 요청했다면 응답으로 제공한다. 기존 Context가 있으면 기록 범위와 완료 여부를 확인해 지속 결정을 연결한다. 전체 작업이 끝나거나 취소된 경우에만 Context를 동결하며, 중간 Steps를 썼다는 이유로 종료하지 않는다. Steps 작성은 Git 실행 권한이 아니다.
