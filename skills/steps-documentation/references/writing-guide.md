# Steps를 읽고 변경을 이해하게 만드는 기준

## 필요한 설명을 고르는 방법

한 문구를 바꾼 작업이면 대상, 전후 문구, 확인 방법으로 충분할 수 있다. 입력·저장·백그라운드 처리·화면 표시가 함께 바뀌었다면 각 역할과 연결을 설명한다. 제목 수나 글자 수를 목표로 삼지 않는다. 긴 문서에서도 같은 내용을 반복하지 않는다.

각 중요한 변경은 “어떤 상황에서 무엇이 잘못됐는가 → 어디를 어떻게 바꿨는가 → 어떤 동작이 달라지는가 → 무엇으로 확인했는가”를 연결한다. 주요 파일 링크는 확인을 돕는 자료이며 설명을 대신하지 않는다. 결과의 이유가 기록에 없다면 이유는 확인하지 못했다고 밝힌다.

전문 용어는 독자가 실제 동작을 떠올릴 수 있게 풀이한다. 예를 들어 “idempotency 개선” 대신 “같은 요청이 재전송돼도 작업을 두 번 만들지 않도록 요청 식별자를 확인한다”라고 설명한다. 꼭 필요한 영어 이름은 괄호나 짧은 주석으로 연결한다. 기본적인 단어까지 모두 번역하거나 별도 용어집을 의무화하지 않는다.

## 설명 수준의 예시

아래는 가상 예시이며 실제 작업의 결과가 아니다.

- 부족한 기록: “worker lifecycle 수정, retry race 해결, 테스트 PASS.”
- 충분한 기록: “응답이 늦으면 같은 작업이 다시 전달될 수 있었다. 기존 처리기는 두 요청을 각각 새 작업으로 저장했다. 변경 후에는 요청 식별자를 저장소에서 확인하고 이미 생성된 작업을 반환한다. 동시 재요청 두 건에서 저장된 작업이 한 개인지 검증했다. 외부 서비스의 실제 재시도 간격은 확인하지 않았다.”

후자의 깊이를 실제 근거가 있는 범위에서 사용한다. 모든 변경에 이런 긴 문단을 붙이거나 예시의 원인·검증을 실제 작업에 복사하지 않는다.

## 표·흐름도·주석

이전과 이후의 책임·상태를 비교할 때 표가 유용하다. 여러 구성요소 사이 데이터 이동이나 분기·재시도를 설명할 때 Mermaid 또는 간단한 화살표 흐름도가 유용하다. 그림의 단계와 이름은 실제 코드·관측과 맞춰야 한다. 없던 계층이나 성능 효과를 그려 넣지 않는다. 그림을 이해하는 데 필요한 조건·예외는 바로 아래 설명한다. 렌더링하지 않았다면 렌더링 확인을 주장하지 않는다.

## 검증 결과와 최종 대조

“테스트 통과”만 쓰지 말고 중요한 검증의 대상·방법·관측 결과와 한계를 설명한다. 실패, 환경상 미실행, 이전 결과의 재사용은 구별한다. 코드나 설정만 보고 실행됐다고 쓰지 않는다.

마지막으로 요청된 범위의 diff와 비교해 중요한 변경·이유·상태 흐름·미완료 사항이 빠지지 않았는지 읽는다. 독자가 원래 대화를 열지 않고 문제와 전후 동작을 이해할 수 있으면 충분하다. 이것은 작성 품질 확인이며 별도 승인이나 새 테스트 단계가 아니다.
