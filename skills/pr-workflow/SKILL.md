# PR Workflow

요청의 완료 지점을 구별한다. **PREPARE**는 제목·본문·리뷰 정보만 제공하며 staging·commit·push·PR 생성/갱신을 하지 않는다. **EXECUTE**는 명시된 PR 생성 또는 지정 PR의 제목·본문 갱신을 수행한다. PR 요청은 미커밋 변경의 자동 commit이나 merge·reviewer 지정을 포함하지 않는다.

적용 지침과 PR 관례, base/head, 커밋된 전체 branch diff를 확인한다. staged·unstaged·untracked는 PR에 아직 포함되지 않은 변경으로 따로 구분한다. 실제 변경, 계약·실행 흐름, 영향, 검증 기록과 제한을 바탕으로 나중에 변경 이력을 읽는 사람도 이해할 제목·본문을 작성한다. Plan/Steps가 없어도 진행하고 확인하지 못한 효과나 검증 성공을 쓰지 않는다. base나 범위가 불명확하면 확인 가능한 초안과 한계를 제공한다. 파일 작성을 요청받았다면 사용자 지정 위치 → 저장소 관례 → `docs/pr/`를 따르고, 설명만 요청됐다면 응답으로 제공한다.

최신 커밋 메시지나 이전 PR 본문만 옮기지 말고 현재 전체 비교 범위의 중요한 목적을 대조한다. 사용자 지정 언어를 우선하고 없으면 저장소의 명시 언어 규칙, 그다음 한국어를 따른다. 저장소에 Conventional Commits 관례가 있으면 제목에도 유지한다. 제목은 파일이나 기술 이름의 나열보다 해결한 문제나 기능 변화를 드러낸다.

본문은 변경이 필요한 이유와 실제 변경, 전후 동작·영향, 수행한 검증과 중요한 미확인 범위를 연결한다. 핵심 결과를 먼저 제시하고 확인되지 않은 원인·선택 이유·효과는 추측하지 않는다. 구현 선택이나 대안은 반영 판단에 필요하고 근거가 있을 때 설명한다. Steps의 상세 구현을 반복하거나 변경 파일 목록으로 설명을 대신하지 않는다.

설명 깊이는 변경에 맞춘다. 작은 변경은 목적과 결과를 짧게 쓰고, 일반적인 기능·버그 수정은 배경과 동작 변화 및 검증을 설명한다. 복합 변경은 관련 구성요소의 영향, 호환성·오류 처리·배포 위험을 필요한 만큼 설명한다. 같은 목적의 변경은 기능별로 묶고 독립적인 목적은 구분한다. 고정된 제목 수, 체크리스트, 표나 다이어그램을 강제하지 않는다. 전문 용어는 이해에 필요한 곳에서 풀어 쓰고 비교가 도움이 되면 표나 짧은 예시를 사용한다.

제목과 본문을 명확히 구분해 GitHub와 Gitea에 바로 복사할 수 있는 일반 Markdown과 실제 줄바꿈으로 제공한다. 리뷰어 지정·승인 요청·리뷰 체크리스트는 실제 필요하거나 요청된 경우에만 포함한다. 수행한 검증의 대상과 결과를 사실대로 적고 중요한 미검증 범위나 위험을 밝힌다. 관련 코드·환경과 실행 근거가 유효하면 기존 검증을 재사용할 수 있으며 PR 작성 자체가 새 테스트나 전체 검사, 별도 승인을 요구하지 않는다.

EXECUTE에서는 [Provider 작업](references/provider-operations.md)을 읽는다. 확정된 committed head를 PR 생성에 필요한 경우에만 허용된 일반 push로 공개할 수 있다. 대상·공개 범위가 모호하거나 push가 금지됐다면 해당 실행을 보류하고 준비 자료를 제공한다. 지정 PR 설명 갱신은 요청된 필드만 수정한다. 성공은 실제 provider 조회의 PR 식별자·URL·head/base·상태로 확인한다.
