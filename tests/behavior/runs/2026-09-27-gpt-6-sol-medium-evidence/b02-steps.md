# 결과 저장에 맞춘 작업 상태 변경 — Steps

## 문제와 원인

작업 생성 시 `api.py`는 메모리 저장소의 상태를 `queued`로 둔다. 이후 백그라운드 작업 처리기인 `worker.py`가 결과를 저장한다. 기존 처리기는 `db.save_result`를 호출하기 **전에** 상태를 `done`으로 기록했다. 그래서 저장 중에도 화면에 `완료`로 표시될 수 있었고, 저장이 `OSError`로 실패해 결과가 없는데도 상태는 `done`으로 남았다. 기존 테스트는 성공 후 결과와 `완료` 표시, 실패 시 예외와 결과 부재를 확인했지만 저장 중·실패 후 상태는 확인하지 않아 이 오류를 잡지 못했다.

이전 세션의 [Context](../context/job-status-save-lifecycle.md)를 현재 코드와 대조했다. 저장 순서 문제는 그대로였지만, 현재 `ui.display`는 상태 문자열 대신 `{'state': ...}` 객체를 받는다. 이번 테스트는 현재 UI 계약에 맞춰 표시 결과도 확인한다.

## 변경한 흐름

| 시점 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 작업 생성 | `queued` | `queued` |
| 결과 저장 호출 중 | 이미 `done` | `running` (`처리 중`) |
| 저장이 정상 반환한 뒤 | `done` | `done` (`완료`) |
| 저장이 예외를 던진 뒤 | 결과가 없어도 `done` | `failed` (`실패`), 예외는 호출자에게 재전파 |

`worker.process`는 먼저 `running`을 기록하고 `db.save_result`를 호출한다. 정상 반환 후에만 `done`으로 바꾸며, 저장 도중 예외가 발생하면 `failed`를 기록하고 같은 예외를 다시 던진다. 이 순서는 기존 호출자의 예외 처리 방식은 유지하면서 상태가 저장 결과를 따르게 한다. `db.py`의 정상 저장 및 `fail=True` 오류 동작, `ui.py`의 상태별 표시 문구는 이미 요구에 맞아 수정하지 않았다.

## 검증과 범위

- `test_flow.py`의 정상 경로는 저장 함수가 실행되는 동안과 정상 반환 직후에 `running`인지, 결과 기록 후 최종 상태가 `done`인지 확인한다. 실패 경로는 저장 중 `running`, `OSError` 전파, 결과 부재, 최종 `failed`를 확인한다. 각 상태의 UI 문구도 확인한다.
- `py -3.10 -B -`로 같은 성공·실패 경로를 직접 실행해 두 상태 전이와 예외 전파를 확인했다. `git diff --check`도 통과했다.
- 설치된 Python 3.10, 3.13, 3.14 환경에 `pytest`가 없어 `test_flow.py` 자체는 실행하지 못했다 (`No module named pytest`).

이 저장소의 `Database`는 메모리 딕셔너리다. 여기서 “저장 성공”은 `save_result`가 정상 반환했다는 뜻이며, 외부 영속 저장이나 동시 작업 간 원자성은 이 변경의 검증 범위가 아니다. 생성 API가 돌려준 `job['state']`는 생성 시점의 `queued` 값이고, 이후 상태는 `db.status[job_id]`에서 읽는다.
