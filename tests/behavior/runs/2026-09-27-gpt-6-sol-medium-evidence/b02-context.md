# 작업 상태와 결과 저장 순서 — Context

## 현재 상태와 요구

- 인계 시점: 2026-09-27, `feat/lifecycle`, HEAD `38b7e89` (`초기 작업 흐름`). 이 문서는 분석과 다음 세션의 구현 준비용이며, 이번 세션에서 동작 코드는 변경하지 않았다.
- 요구 계약: 작업 처리 중에는 `running`을 유지한다. 결과 저장이 성공한 뒤에만 `done`으로 바꾸고, 저장 실패 시 `failed`로 표시한다.

## Analysis: 확인된 흐름과 원인

| 경계 | 현재 동작과 근거 | 영향 |
| --- | --- | --- |
| 생성/API | `api.py:4-7`의 `create_job`은 새 `Database`를 만들고 `db.status[job_id]`를 `queued`로 설정한다. 반환하는 `job['state']`는 생성 시점의 별도 값이다. | 반환한 `job`은 이후 DB 상태를 자동으로 반영하지 않는다. 이 코드에는 상태 조회 API가 없다. |
| 처리/worker | `worker.py:1-4`의 `process`는 저장 전에 상태를 `done`으로 바꾼 뒤 `db.save_result`를 호출한다. `running` 설정과 실패 처리 분기가 없다. | 저장 중에도 상태가 `done`이며, 저장 실패 시 예외가 전파되고 상태는 `done`으로 남는다. |
| 저장/DB | `db.py:1-9`는 상태와 결과를 메모리 딕셔너리로 보유한다. `save_result(..., fail=True)`는 결과 쓰기 전에 `OSError`를 던진다. 정상 경로에서만 `results[job_id]`를 기록한다. | 이 저장소에서 확인 가능한 성공 기준은 `save_result`의 정상 반환이다. 외부 영속 저장이나 트랜잭션은 구현되어 있지 않다. |
| 표시/UI | `ui.py:1-2`의 `display`는 `queued`, `running`, `done`, `failed`를 각각 한국어로 변환한다. 상태를 읽거나 갱신하지는 않는다. | 표시 문자열은 이미 준비되어 있으나, 실제 상태 생산자가 `running`과 `failed`를 사용하지 않는다. |
| 검증 | `test_flow.py:7-19`는 정상 저장 후 `done`과 결과, 실패 시 예외 및 결과 부재만 확인한다. | 저장 중 상태와 실패 후 상태를 확인하지 않아 현재 오류를 놓친다. |

`python -B -`로 직접 실행한 관측: 정상 저장 후 `{1: 'done'}`과 `{1: 'output'}`이 남았다. `fail=True`에서는 `OSError('storage unavailable')`가 발생했고, 결과는 `{}`였지만 상태는 `{2: 'done'}`이었다. `python -m pytest -q -p no:cacheprovider`는 이 환경에 `pytest`가 없어 실행되지 않았다 (`No module named pytest`).

## 영향 범위와 종료 근거

상태 생산자는 `api.py`와 `worker.py`, 저장 동작은 `db.py`, 상태 소비자는 `ui.py`와 테스트다. 이 작업 디렉터리의 Python 파일은 이 다섯 개이며, 전체 텍스트 검색에서 다른 상태 기록자나 결과 저장 호출자는 확인되지 않았다. 따라서 현재 확인된 동작의 핵심 수정 지점은 `worker.py`이고, 회귀 검증은 `test_flow.py`에 필요하다. `ui.py`의 매핑 자체는 요구 상태를 이미 지원한다. 별도 프로세스, 외부 DB, 브라우저 연동은 이 코드에서 확인되지 않았다.

3. 저장 호출 중 관측되는 상태가 `running`인지 확인하는 테스트를 추가한다. 정상 반환 후 결과와 `done`, 저장 실패 후 결과 부재와 `failed`를 함께 검증한다. 기존 `OSError` 전파 여부도 명시적으로 검증한다.
4. 테스트 도구를 사용할 수 있는 환경에서 관련 테스트를 실행한다. 이 환경을 그대로 쓴다면 먼저 `pytest` 가용성을 확인한다.

## 미확정 사항과 판단 기준

- 예외 계약: 현재 `process`는 저장 `OSError`를 호출자에게 전파한다. 요구는 실패 상태를 지정하지만 예외를 삼키거나 반환값을 바꾸라고 하지는 않는다. 기존 호출자 계약을 유지하면서 `failed`를 기록하고 재전파하는 방향이 현재 근거에 가장 가깝다. 다른 호출자가 생겼는지 다음 세션에 재확인한다.
- 동시성/원자성: 현재 구현은 단일 프로세스 메모리 딕셔너리이며 동시 실행이나 실제 영속 저장에 대한 보장을 보여주지 않는다. 따라서 이 분석으로 외부 시스템의 원자성까지 보장한다고 판단하지 않는다.
- 생성 응답의 `job['state']`: 초기 상태 스냅샷으로 보인다. 요구의 처리 중/완료/실패 표시가 그 반환 객체 자체의 갱신까지 뜻하는지는 명시되지 않았다. 현재 상태의 직접 관측 지점은 `db.status[job_id]`다.

이 Context는 구현 후 실제 변경·검증 결과에 맞춰 갱신하고, 완료 사실은 별도 작업 기록에 남긴다.
