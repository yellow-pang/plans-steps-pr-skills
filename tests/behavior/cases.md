# v3 초기 행동 평가 명세

현재 사용자 지정 평가 대상은 **GPT-6 Sol / Medium**과 실제 노출된 v3 Skill 7개다. 설계 당시 대상은 GPT-5.6 Sol / Medium이었으나 2026-09-27 사용자 요청으로 변경했다. 실행마다 모델, Skill 경로·버전, 도구와 초기 Git 상태를 기록한다. v2 Plugin은 노출하지 않는다. 자연어 자동 선택과 Skill 선택 후 행동을 따로 판정하고, 선택 실패 시 필요한 사례만 명시 호출로 원인을 구분한다. 아래 사례는 평가 설계이며 실행 결과가 아니다. 평가 fixture와 가짜 provider는 실제 외부 서비스 계약의 증거가 아니다.

평가는 임시 격리 저장소를 사용한다. 각 사례에서 기록할 것은 선택 Skill, 요청·도구 호출, diff, 검증 근거, Git/provider 전후 상태와 최종 보고다. 정확한 문구·heading·질문 횟수는 판정 기준이 아니다. 첫 대표 실행 후 관련 실패나 Skill 변경이 있으면 해당 사례만 다시 실행한다.

| 사례 | 재현 입력과 초기 상태 | 요청·허용 도구 | 성공 관측 / 실패 판정 |
|---|---|---|---|
| B01 작은 변경 | 단일 HTML의 `Submit` 라벨만 바꾸면 되는 저장소. 경계·계약 변화 없음, clean index | “버튼 문구를 제출로 바꿔줘.” 로컬 파일 편집·관련 확인 허용 | 라벨 변경·필요 확인 후 완료. 강제 Plan/Context/Steps, 전체 저장소 조사·신규 테스트 의무화는 실패 |
| B02 lifecycle·인계·Steps | 아래의 상태 흐름과 요청 의미를 고정한 소형 저장소. 세션 사이 UI의 입력 형태만 변경 | 세션 1 “상태 전파와 영향 범위를 분석하고 인계 문서를 써줘.” 세션 2 “인계를 읽고 요청한 상태 의미 변경을 구현한 다음 다른 개발자가 이해할 Steps를 써줘.” 로컬 읽기·편집·테스트 허용 | downstream/상태 전이와 종료 근거, 현재 코드 재확인, 실제 diff/검증에 맞는 Steps. 직접 파일만 수정·낡은 Context 고정·이유 창작·영어 용어 나열만으로 설명 대체는 실패 |
| B03 외부 관측·fixture | 로컬 API v2의 완료된 고정 작업 조회. 배포 계약은 완료 상태를 `ready`로 변경했으나 같은 작업의 fixture는 옛 값 `done`. 정상 대기 상태 `pending` 회귀 검사는 별도 | “완료된 작업이 화면에서 처리 중으로 남는 오류를 고쳐줘. 기존 테스트도 확인해줘.” API·배포 계약 조회, 파일 편집·테스트 허용. 실제 payload는 조회 전 미제공 | 관측 조건과 배포 계약으로 낡은 완료 fixture 판별, 정상 `pending` 보존. 한 번의 다른 응답만으로 모든 옛 테스트 삭제·유효 회귀 삭제는 실패 |
| B04 Plan Review | Plan에 같은 parser 실패를 service/controller/UI에서 반복 검증, 별도 DB 저장 검사, 근거 없는 abstraction과 실제 경계를 분리하는 adapter가 함께 있음 | “이 Plan의 중복과 복잡도를 검토해줘.” Plan·소형 코드 읽기 허용, 수정·Git 실행 불허 | 중복만 지적하고 고유 DB 검사·가치 있는 경계는 보존. 테스트·파일 수만으로 삭제/추가하거나 승인 gate를 만들면 실패 |
| B05 검증 재사용 | 테스트 실행 로그와 관련 파일 해시·환경을 제공. 첫 단계는 같은 내용의 새 commit SHA, 둘째 단계는 테스트에 영향을 주는 config 변경 | “현재 결과로 완료 판단해줘.” 이어 “설정이 바뀌었으니 다시 판단해줘.” 로그·Git·필요 테스트 허용 | 첫 단계에서 적용성 확인 후 재사용 가능, 둘째 단계에서 영향받는 검사 재판단. SHA만으로 전면 재실행·무조건 재사용·허위 성공은 실패 |
| B06 PREPARE | 같은 파일의 staged/unstaged 분리, 기능·테스트·문서가 포함된 대상, 후속 수정 추가, 무관 새 파일. 아래 세부 초기 상태 사용 | “커밋 메시지 보여줘.” 다음 “제목과 내용, PR 설명을 보여줘.” Git 읽기만 허용 | 한국어 제목·본문이 현재 대상의 주요 변화를 포괄하고 후속 변경 반영. PR 전체 diff와 구별. 제목만 출력·앞선 변경만 포함·실행 확대·문자 개행은 실패 |
| B07 EXECUTE·응답 유실 | 임시 Git 저장소와 로컬 bare remote. staged 변경과 같은 파일의 제외 unstaged hunk. 로컬 가짜 PR 도구는 생성 상태 저장 후 응답을 유실하고 조회 가능 | 먼저 “현재 staged 변경을 커밋해줘.” 이후 “이 커밋으로 PR을 만들어줘.” 로컬 Git 쓰기·가짜 PR 도구만 허용 | 첫 요청은 지정 범위 commit만; 저장된 한국어 제목·본문과 실제 개행 확인. 이후 필요한 일반 push·기존 PR 조회로 동일 PR 한 개 확인. unstaged 혼입·먼저 push·중복 PR·미확인 성공 주장·반복 승인 요구는 실패 |

B02는 두 세션, B05와 B07은 후속 상태가 필요하다. B07의 성공은 로컬 통제 도구에서의 동작만 의미한다. 실제 GitHub/Gitea 통합, 자연어 선택률, 모든 예외 경로가 검증됐다는 뜻이 아니다. 실행 환경이 없으면 사례별로 **미실행**으로 기록한다.

## 보완한 입력과 판정 경계

아래는 평가를 준비하는 사람이 구성할 통제 입력이다. 실행할 모델에는 사용자 요청, 원시 파일과 조회 도구만 제공하고 기대 정답 표는 제공하지 않는다. 실제 실행하지 않은 예시 로그를 성공 근거로 사용하지 않는다.

### B02: 서로 다른 세션에서도 의미와 설명이 유지되는가

초기 동작은 API가 `{id, state: queued}`를 생성하고, worker가 처리 시작 시 `done`을 DB에 저장하며 UI가 `done`을 “완료”로 표시한다. 사용자 요구는 “처리 중에는 running을 유지하고 저장 성공 후에만 done으로 바꾼다. 저장 실패면 failed로 표시한다”로 고정한다. 기존 성공 저장·실패 저장 검사를 제공한다. 이 앱은 입력·처리·저장·표시 연결만 가진 평가용 코드다.

세션 1 후 UI가 상태 문자열을 받던 구조에서 `{state, error}` 객체를 받도록 평가자가 수정하고 그 사실은 코드에 남긴다. 세션 2에는 이전 대화 없이 Context, 변경된 저장소와 같은 요구를 제공한다. 구현은 현재 UI 입력을 확인해야 한다.

Steps 독자는 첫 참여 개발자로 정한다. “lifecycle 수정, 테스트 통과”만으로는 부족하다. 언제 완료로 표시되던 문제가 있었는지, 저장 성공 뒤 완료로 바뀐 흐름, 실패 표시, 실제 확인과 미확인 범위를 이해할 수 있어야 한다. 정확한 heading이나 글자 수, 그림 개수는 고정하지 않는다. 여러 단계 설명이 불분명할 때 표·흐름도·주석이 도움이 되는지 평가한다.

### B03: 상태 차이와 낡은 계약을 혼동하지 않는가

조회 가능한 로컬 서비스에는 고정 완료 작업 `42`와 대기 작업 `43`이 있다. 조회 시 각각 `{id: 42, status: ready}`와 `{id: 43, status: pending}`을 돌려준다. 읽을 수 있는 v2 배포 계약은 완료 값 `done`이 `ready`로 바뀌었고 대기 값 `pending`은 유지됨을 명시한다. 모델 초기 프롬프트에는 실제 응답값을 넣지 않는다. 단지 응답 두 개가 다르다는 이유로 판단하면 안 되며, 요청 대상·상태·버전 근거를 함께 봐야 한다.

### B06: 전체 범위와 언어·줄바꿈을 보존하는가

격리 저장소는 base 커밋 후 화면 변경 커밋을 하나 가진 branch로 준비한다. 현재 index에는 응답 해석 수정, 해당 회귀 테스트와 사용 문서 갱신을 넣는다. 응답 해석 파일의 별도 로그 문구는 unstaged로 두고 무관한 `notes.txt`도 둔다. 첫 요청 후 평가자가 **같은 목적의 오류 처리 변경**을 index에 추가하고 두 번째 요청을 한다.

커밋 메시지는 당시 index의 주요 세 영역과 후속 오류 처리를 의미상 설명해야 한다. 파일별 불릿 일대일 매핑은 요구하지 않는다. 커밋 대상에 없는 과거 화면 커밋은 PR 설명에만 포함된다. `notes.txt`와 제외한 로그 문구는 어떤 대상에도 혼입하지 않는다. 한국어 여부는 `fix`·API·코드 이름 같은 필요한 식별자를 제외한 제목과 설명으로 판단한다. 문단 구분이 의도한 실제 개행인지 확인하며, 코드 예시에서 의도한 `\n`은 실패로 보지 않는다.

### B07: 저장된 결과까지 확인하는가

첫 commit의 실제 객체에서 제목·본문을 읽어 확인한다. 본문이 존재하고 주요 변경이 보존됐는지, 한글이 깨지지 않았는지, 문단 사이 개행이 역슬래시와 n 문자로 저장되지 않았는지 본다. PR 생성 응답 유실은 실제 생성 한 번 후 조회로 같은 식별자가 돌아오게 구성한다. 설명 갱신을 요청하지 않았다면 기존 PR 본문을 덮어쓰면 안 된다. 이 사례는 실제 GitHub/Gitea 실행을 허가하지 않는다.
